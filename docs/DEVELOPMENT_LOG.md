(The plan as it was agreed and the notes from each milestone, in the order the work happened. For how to use or build the radar read the README and `docs/USER_GUIDE.md` / `docs/BUILDING.md`.)

## 1. Goal
A live air-traffic radar on the VIEWE UEDX80480070E-WB-A: rotating sweep, aircraft plotted by bearing/range
from a configurable home position, nearest-aircraft list and stats, full touch UI, on-device **and** phone
setup, SD-card logging, configurable units/standards, map-based location picking with automatic timezone,
and OTA updates. Data from `api.airplanes.live` over Wi-Fi (no receiver hardware).

## 2. Verdict on feasibility
**GO — every hardware dependency measured on the actual board:** MCU/PSRAM/flash · panel clean at 12–16 MHz
(25/20 MHz fail with this driver) · touch incl. multi-touch · Wi-Fi · live API fetch + filtered parse ·
microSD (64 GB SDHC, FAT, write/read-back verified, ~0.6 MB/s write).

## 3. Technical decisions
| Area | Decision | Why |
|---|---|---|
| Framework | Arduino on pioarduino 54.03.21 (core 3.2.x / IDF 5.4), PlatformIO 6.1.19 via `~/.platformio/penv/bin/pio` | Same pinned toolchain as the RC-Radio projects; builds the diag |
| Graphics | **Espressif esp_lcd RGB in DIRECT mode (no bounce buffer), 16 MHz (~31 Hz), two framebuffers flipped by the driver**; LovyanGFX only for drawing into sprites/tiles (internal-RAM tiles, per-pixel sweep LUT, double-buffered with last-frame sync) | Bounce-buffer mode desynchronises permanently after a late interrupt (see `hardware-findings.md` → DISPLAY DECISION v2); direct mode has no per-chunk interrupt. LovyanGFX's own RGB driver kept as fallback modes (L12/L16) |
| Touch | Own GT911 driver (task polls ~8 ms → event queue), scan 0x14 + 0x5D, multi-touch (5 pts) | LovyanGFX's touch layer reported nothing; direct driver verified |
| Data | `GET /v2/point/{lat}/{lon}/{nm}` every ≥5 s on core 0, ArduinoJson **filter**, double-buffered; dead-reckon between polls | Original's 64 KB doc / whole-String approach is fragile in busy airspace |
| Security | TLS with CA bundle + NTP time (not `setInsecure()`) | Original disables cert checks |
| Config | NVS: Wi-Fi, lat/lon, tz, radius, units/standards, brightness, log/OTA options; `config/secrets.h` = dev defaults only | Change everything without reflashing |
| Storage | SD (FAT32) CSV logs via SPI (CS10 CLK12 MOSI11 MISO13) | Verified |
| Updates | USB (UART port, 230400) + OTA (two-slot `default_16MB`) | See M7 |
| License | GPL-3.0-or-later | Derived from mircemk's GPL-3.0+ sketch |

## 5. Risks and mitigations
| Risk | Likelihood | Mitigation |
|---|---|---|
| Panel jumps under load (16 MHz had jumps; 12 MHz clean in tests) | Low–Med | 12 MHz default; dirty-rect drawing, no full-frame clears, no flash writes while drawing; upgrade path = `esp_lcd` + bounce buffer |
| 12 MHz refresh is ≈ 23.5 Hz (vs ≈ 49 Hz at 25 MHz) | Known | Fine for a radar; caps visible animation near 23 fps; revisit with bounce-buffer backend if wanted |
| Offline map + city/timezone data size & licensing (Natural Earth public domain; GeoNames CC-BY needs attribution; tzdb public domain) | Med | Store on flash partition or SD; credits in About screen; coarse data first |
| Timezone from nearest city is approximate near borders (zones with different DST rules) | Med | Manual timezone override always available |
| Phone setup AP has no internet → map tiles can't load in AP mode | Known | AP only for SSID/password; map picker runs on the home LAN where the phone has internet |
| OTA brick risk (no bootloader rollback in stock Arduino libs) | Low | Boot-failure counter reverts slot; USB recovery always available (UART port) + factory backup |
| airplanes.live terms/rate limit unverified (docs page returned 403; "~1 req/s, non-commercial" from memory) | Med | Poll ≥5 s; User-Agent; provider URL configurable (adsb.lol / adsb.fi style APIs are candidates — **to verify**) |
| GT911 address varies per boot | Known | Probe both addresses every boot (done) |
| 2.4 GHz-only Wi-Fi | Known | Documented; shown in setup UI |
| Visual checks depend on you (I can't see the screen) | Known | On-screen status line + serial self-test; you send photo/video for sign-off |

### M4 results (2026-10-09)
**Does it disconnect the unit?** Not in normal use. Nothing changes the Wi-Fi unless you start a change: a *scan* briefly interrupts the link (2–4 s, the radar keeps going on dead reckoning), *Setup From Phone* runs an access point **alongside** the existing connection (AP+STA), and *joining another network* is the only step that drops the old link — if the new one fails the radar re-joins the old one by itself (verified: wrong password → "Wrong password?" after ~3 s → back on the saved network, next fetch fine). Saved credentials live in NVS and survive firmware flashes.
**Wi-Fi manager (`wifimgr`)**: join/scan/AP state machine, connection watchdog (moved out of `main`), cached status for the screen (driver queries can block while the radio is busy), disconnect-reason based failure messages (wrong password / network not found / no answer).
**On the device** — Settings > **Wi-Fi** tab: current network + signal, *Change Network* (scan list with signal bars and lock marks, rescan, up/down, "Other network..." for hidden names), on-screen **QWERTY keyboard** (shift, 123/symbols, Del with key repeat, Show/Hide for passwords, field counter), connect progress screen with Try Again / Back, *Setup From Phone*, web address, **web PIN**, IP address. With no network saved the radar opens the phone-setup screen by itself.
**From a phone** — *Setup From Phone* starts the access point `ADSB-Radar-XXXX` (WPA2, random 8-character password created on first boot, shown on screen and in a **QR code** that phones join with one scan). A DNS server answers every name with the radar so the phone pops up the setup page (captive portal; probe URLs for Android, iOS and Windows are redirected). The access point rules are described under "Third round" below.
**Web interface** — `http://radar.local` (mDNS) or the IP address; one self-contained 10 KB page, mobile-first: status, range/trail/brightness/diagnostics, font and the four colours, units, location (name, lat/lon, country, time-zone list or POSIX string), Wi-Fi scan/connect, restart. Phones on the setup access point are trusted (they hold the WPA2 password); everyone else must enter the 6-digit **PIN** shown under Settings > Wi-Fi (cookie session, 5 wrong tries lock the login for a minute). It is plain HTTP, so the PIN travels unencrypted on your LAN: keep it to a trusted network. API (JSON): `/api/login`, `/api/state`, `/api/set`, `/api/wifi/scan`, `/api/wifi/join`, `/api/wifi/status`, `/api/restart`.
**Measured:** LAN API verified with curl (login incl. wrong PIN, state, setting changes, scan); screens verified from framebuffer dumps (Wi-Fi tab, network list, keyboard, phone-setup/QR, join failure); rollback verified on the board. Heap with the web server running: idle 98 KB, low-water 42 KB (TLS fetch), PSRAM unchanged.
**Not yet exercised on hardware (needs a phone):** joining the setup access point and the captive-portal pop-up; completing a join from the phone page (the access point changes channel when the radar joins your router, so the phone may need to re-join your home Wi-Fi — the page says so); the no-network-saved first boot; a *successful* join from the on-screen keyboard (only the failure path was run, to avoid typing your real password).
**Bug found by the user after M4 ("after pressing scan networks nothing is shown and the web is stuck") — fixed:** the web server's own writer gives up after ~10 quick retries when the TCP send buffer is full, which cut the 10 KB page short on a busy link (browser: `ERR_CONTENT_LENGTH_MISMATCH`), so the page script never ran and every button was dead. The page is now sent by a writer that keeps going until all bytes are out (40 sequential and 12 parallel loads all complete), the page shows "did not load completely — Reload" if its script is missing, every request has an 8 s timeout, and scanning is hardened: the scan starts 0.4 s after the answer has left (the radio hops channels), a failed or hung scan is abandoned after 15 s instead of reporting "scanning" forever, the network list is scanned once when the setup access point starts and reused while a phone is attached (a rescan interrupts the phone's connection for a few seconds; pressing Scan twice forces a fresh one). Verified in a real browser (Scan: 4 networks in 4 s).
**Second round of user feedback (phone on the setup access point, used the IP address):** (1) *no automatic redirect to the portal* — the access point's DHCP server never offered a DNS server (the Arduino/IDF AP only does so when `softAPConfig` is given one), so phones could not resolve their connectivity-check names and never raised the sign-in page. `startAP()` now calls `softAPConfig(192.168.4.1, gw 192.168.4.1, /24, lease from .2, **dns 192.168.4.1**)` before `softAP()`; checked from the Mac against the radar's DNS server (any A query answers 192.168.4.1, AAAA answers empty NOERROR) and the probe URLs (`/generate_204`, `/hotspot-detect.html`, `/connecttest.txt`, `/ncsi.txt` → 302 to `http://192.168.4.1/`). The phone-side pop-up itself still needs confirming on a phone. (2) *SSID not filled in after choosing a scanned network* — the web page now has an always-visible, editable "Network name" field that is filled when a scan result is picked (and focuses the password; notes open networks); the select starts with "Choose a network (N found)" so picking the first one fires a change too.
**Third round (user: "it remains on the captive portal, it should close"; "the pairing AP should only be active when the setup screen is on the display, and stop when connection is made"; "constantly active when the network was never configured or when not found"):** the setup access point now follows one rule set in `wifimgr`: it runs (a) while the setup screen is on the display, and (b) continuously, with no time limit, while the radar has nothing to connect to — no network was ever saved, or the saved one has been unreachable for 30 s ("not found"; the radar's status text then says "Setup Wi-Fi is on: Settings > Wi-Fi"). It switches off 4 s after a connection is made (long enough for the phone's page to read the result) and, for (a), when the screen is left; in case (b) it also switches off the moment the saved network is reachable again. While a phone is attached in case (b) the station's reconnect attempts are paused (their channel scans would otherwise knock the phone off every few seconds). To make the phone's sign-in sheet close by itself, the radar answers the phones' internet checks with a redirect to the setup page while setup is pending and with the answers each system expects once the connection is made (Android 204, Apple "Success", Windows NCSI/connect-test, Firefox `success`). Verified with the Mac as a client (probes: 302 → 204/200 → access point gone) and with timeline tests: setup screen up/down, "no network saved" (dev `N`) stays on until cleared, "not found" (dev `w` outage) comes up after ~30 s and goes off on reconnect. Not verified on an iPhone: the sheet closing itself, and the iPhone's earlier "unable to join" via the QR code (joining by hand worked; the radar side showed the join in its log). Dev: `N` pretend no network, `K` pretend setup finished.
New dev commands: `H` heap probe, `P<role>,<swatch>` palette, `X`/`Z` tap/pinch injection, `D` screen dump.

### M6 results (2026-10-09)
**Logging** (Settings > **Log**, also the phone page): while it is on, the radar appends **one CSV per UTC day** (`/adsb/2026-10-09.csv`: `time_utc,hex,callsign,lat,lon,alt_ft,gs_kt,track,squawk`) and a **system log** (`/adsb/sys-2026-10-09.log`: boot with reset reason, data restored/failing, card events, logging switched on/off). An aircraft is written at most once per 10 / 30 / 60 s (default 30 s; ~20 MB/day in busy airspace). Nothing is written before the clock is set. Squawk codes are now read from the feed.
**Design:** a background task owns the card (SPI2, 20 MHz, verified in M0: 64 GB SDHC FAT, ~580 KB/s). Producers only append to RAM buffers (96 KB / 16 KB in PSRAM), so the radar never waits for the card; the task writes whole lines in batches every 5 s, opening and closing the file each time, so pulling the card loses at most the last few seconds. **Removal and re-insertion without a reboot:** a failed write or a card that stops answering (checked every 15 s) marks it lost; the buffers keep filling and the card is re-mounted every 10 s; when it is back the buffered rows are written. **Tested** by simulating removal for 36 s: 20 rows logged during the outage appeared in the file afterwards with correct timestamps, 0 dropped. **Retention:** the oldest day files (never today's) are deleted while less than 10 % of the card is free; checked at mount and hourly. **Eject/Mount** (Log tab, phone page) flushes and unmounts so the card can be pulled safely.
**Interface:** Log tab = card size/free, logging on/off, interval, today's rows/bytes, Eject/Mount, **View Logs** (file list newest first → viewer of the last ~12 KB of the chosen file, scrolled by lines). **Status icon** on the radar's status text: palette colour = logging, grey slash = off, orange cross = no card or write problem, amber arrow = ejected. The phone page shows the same status.
**Memory (important):** adding the SD stack, the route cache and the Location/Log screens pushed the lowest free internal RAM during a secure fetch from 39 KB to 17 KB (one start-up dip hit 1.6 KB). Cause: a TLS connection takes ~45 KB of internal RAM (two 16 KB record buffers + handshake state). Fix: `src/tls_psram.cpp` overrides mbedTLS's two allocation hooks (`esp_mbedtls_mem_calloc/free`) so TLS memory comes from PSRAM; a secure connection now costs ~3 KB of internal RAM (idle 68 KB, 65 KB free right after the handshake; fetch time unchanged at ~1.8 s). The aircraft JSON document also parses into PSRAM. (The `MBEDTLS_*_MEM_ALLOC` lines in `platformio.ini` have no effect, the mbedTLS libraries are prebuilt — drop them at the next library rebuild.)
**Not included:** downloading log files over the web (streaming a 20 MB file would block the radar's main loop; needs its own task) — read them on the radar's viewer or with the card in a computer.
**Dev commands:** `V` prints card status, file list and the tail of the newest files; `U` simulates pulling/returning the card.

### Publication test run (2026-10-11, after the M8 soak)
The device tests (`tests/device_tests.py`) were run for the first time on the real radar, after the soak, and found real faults. All fixed, then the whole suite passed (17 tests, 2 skipped, see [TESTING.md](TESTING.md)).
- **A stalled request restarted the radar.** The Arduino `WebServer` parses a request in one blocking go (every read waits up to 5 s for the next byte). A client that sent half a request and stopped (or sent a byte at a time) kept the main loop inside `handleClient()` until the 15 s
  loop watchdog fired: the radar restarted (backtrace: `Stream::readStringUntil` in `WebServer::_parseRequest`). Fix: `GuardedServer` (`webui.cpp`) accepts the connection itself and starts the parse only when all headers and a small body (peeked from the socket) have arrived; incomplete requests are dropped after 3 s.
  Two details cost an extra flash each: lwIP's `MSG_PEEK` shows only the first TCP segment (Python sends headers and body separately, so the body is judged by `available()` instead), and the library accepts and parses in the same call, so the accept had to move into the guard.
- **`/api/state` took 650 ms**, blocking the main loop (about 20 frames) on every poll of the phone page (and of the soak monitor, which explains part of the soak's few slow-frame samples). Cause: `esp_ota_check_rollback_is_possible()` verifies the whole other slot (a SHA-256 over 5 MB) on every call.
  Now asked once per boot. The state answer takes about 50 ms, and 150 sequential requests plus 12 parallel ones went from 127 s to 13 s.
- **The photo was never drawn on a card that also shows FlightAware lines.** A 200×133 thumbnail plus its two credit lines did not fit between the card text and the footer, and the room check silently skipped it. The photo is now scaled (box filter, never enlarged) into a 220×96 box and the check uses the real font height.
- **The frame-rate figure froze while the settings screen was open** (only the radar's own frame counted). It now counts every displayed frame.
- **A slow link could restart the radar.** The Arduino `HTTPClient` reads a response body in loops that poll the socket with `yield()`, which never lets the idle task run. A 60 KB airplanes.live answer (a 50 nm radar over London lists 100+ aircraft) trickling in at a few kB/s
  kept the data task busy on core 0 for more than 15 s and the idle-task watchdog restarted the radar (twice, during the screenshot session; backtrace in `NetworkClientSecure::available()` under `HTTPClient::writeToStreamDataBlock`). The soak never met it because its answers were 4 KB and took 1.6 s.
  Both big readers (`adsb.cpp`, `flightinfo.cpp`) now read the body in a loop that sleeps between polls (the OTA link download already did), and the stand-in server has a slow mode (`MOCK_SLOW_SECONDS`) that was used to check a 25 s trickle: no restart.
- **The serial screen dump restarted the radar too:** the Arduino core's `log_e()` writer busy-waits for the UART to go idle, which a minutes-long dump never allows, so a log line from the data task spun core 0 until the same watchdog fired. The dump now switches that output off while it runs and numbers its rows
  (a line another task garbles costs one row). For documentation pictures there is also a developer-only `/api/screen` (build flag `DEV_SCREENSHOT`, PIN required) and `tools/devtools/radar_screen.py`.
- **Tests that could harm a real radar:** the flight-key test replaced the stored key and then cleared it. It now skips itself on a radar that has a key (the key cannot be read back). A malformed multipart upload makes the server close the connection without an answer; the test accepts that.
- **Tools:** opening the serial port restarts the board on macOS with the CH340 (so `Y` demo locations set by a separate command were lost); `radar_serial.py run` keeps one session. The `Y` demo location now switches saving off until the next restart (it used to live only in RAM, but any settings change would have written it to flash).

### Flight details, aircraft card, country and flag (2026-10-10, after M8)
**Aircraft card moved into the info panel (user request).** Selecting an aircraft now replaces the aircraft table (right panel) with its card, so nothing covers the radar and there is room for everything: callsign and type, **country of registration with its flag**, airline, model, route, **take-off time, ETA, delay, flight status and progress bar**, altitude/speed, distance/bearing/track, registration and ICAO address, and a **photo** with the photographer's credit. Tapping the card (or an empty part of the radar, or the same aircraft) brings the table back; other aircraft are selected by tapping their marks while a card is up. The status text (Live ADS-B, aircraft count, warnings, emergency banner) stays at the top left of the radar.
**Country and flag (no key, no network):** the country comes from the aircraft's ICAO 24-bit address (state of registry, ICAO Annex 10 Table 9-1, `tools/icao_ranges.txt`); my first hand-typed table was wrong for Central America, so the table was rebuilt from the official PDF by `tools/build_icao_ranges.py` and checked against live aircraft (30 aircraft in 16 states, including Jamaica, Panama and Trinidad: no disagreement; an earlier 100-aircraft run found the three errors that led to the rebuild). Flags: 189 national flags drawn for this project (`tools/build_flags.py`, 27x18 px, simplified emblems), embedded as `flags.bin` (184 KB). Shown for every aircraft with a normal ICAO address (not for TIS-B "~" addresses).
**FlightAware + photo (optional, off by default):** Settings > **Flights Data** (also on the phone page): enable, API key (on-screen keyboard, never shown again), contact e-mail (sent in the User-Agent to Planespotters, as they ask), photo on/off, flown-track on/off, *Test Key* (calls `/account/usage`), and the last result or error. When enabled and an aircraft stays selected for 1.5 s: `/flights/{callsign}` (the in-flight one is picked from the list), then `/flights/{fa_flight_id}/track` (drawn as a line on the radar, up to 300 points), then Planespotters for a photo (progressive JPEGs: decoded with stb_image into PSRAM). Cache 10 minutes, ceiling 60 FlightAware calls an hour, one HTTPS exchange per pass of the data task so the aircraft fetch is never held up for long. FlightAware's route replaces adsbdb's when it answers; its errors show on the card ("FlightAware: Key rejected (401)").
**Testing without a key:** `tools/mock_aeroapi.py` answers like AeroAPI (key `TESTKEY`); a build with `-DFA_BASE="http://<computer>:8100/aeroapi"` talks to it. Verified on the radar: key test accepted/rejected, flight lookup, 300-point track drawn across the radar, real Planespotters photo downloaded and decoded (progressive 200x133 JPEG, 5-10 KB), card layout, error line with a wrong key, dismissal. **Not verified:** a real FlightAware answer: the parser follows the documented v4 field names (`flights[]`, `actual_off`, `estimated_on`, `origin.code_iata`, `positions[]`...), so a field that differs would show as missing times; the Flights Data page's last-result line says what happened.
**Flash:** 5.1 MB of the 6.55 MB slot.

### M8 results (2026-10-10)
**Emergency squawk highlight (7500 hijack / 7600 radio failure / 7700 emergency).** An aircraft squawking one of these codes is drawn as a filled red mark with two heavy rings and a red label with its code ("BAW123 7700"); it never fades. Its row in the aircraft table gets a red frame, red callsign and the code in the Type column. The status area shows a blinking red banner ("7700 EMERGENCY", callsign, distance, bearing; "+more" if several), the info card gets a red frame and the code, and the phone page shows a red line under Status. A new emergency is written once to the SD system log (callsign, hex, registration, position, altitude). **It overrides everything else (user request):** red whatever the palette, normal colours and **full backlight** even while night mode is on; the override lasts while the squawk is on the radar and two minutes after. Test: serial `E3` (or `E1`/`E2`, `E0` off) makes the nearest aircraft squawk 7700; verified on the framebuffer, including with night mode on.
**Night mode** (Settings > Radar > *Night Mode*: Off / Auto / On; phone page too). While it is in force the backlight follows *Night brightness* (default 10 %, 2-100 %, finer steps near the bottom; the Look page's Brightness row edits whichever applies) and every colour role is the red swatch, including altitude marks, map overlay, table dots and the sweep. **Auto** = the sun is more than 1 degree below the horizon at the radar's location (almanac formula, about 0.1 degree accurate; needs the clock). The last state is stored, so a restart at night does not flash a bright screen before the clock is set. Off is the default. Row text: "Auto (on now)" / "Auto (off now)".
**Lines & Buttons colour** (Settings > Look, phone page): a fifth colour role for frames, separators and buttons: the radar-area frame, the four on-screen buttons, the aircraft-table frame and separators, the info card frame, the whole settings screen's frames/buttons/tabs. Existing installs start with the Radar colour (the previous look). The settings rows are 54 px high so seven fit on the Look page.
**Hardening.**
- *Loop watchdog:* the main loop is now watched too (`enableLoopWDT`, 15 s). Long jobs feed it (web upload, flash install, espota, slow clients, screen dump). Tested with serial `Q` (blocks the loop 20 s): the radar restarted after 15 s and the next boot's system log said `boot after a crash: reset reason 6 (watchdog) ... main loop in 'frame'`. The main loop now leaves a breadcrumb (wifi / web / settings / frame) like the other tasks.
- *Health monitor* (`main.cpp`): no aircraft data for 15 minutes with Wi-Fi up, or Wi-Fi down 30 minutes with a saved network, or the display interrupt not counting frames for 15 s (not during updates) logs the reason and restarts the radar. At most one such restart per 15 minutes by construction. Wi-Fi loss/recovery ("wifi lost", "wifi connected: ..., was offline 46 s") and an hourly line (uptime, heap and low-water mark, PSRAM, signal, fetches ok/failed) go to the SD system log.
- *Wi-Fi reconnect:* the 60-second re-join watchdog (M4) was re-tested with serial `w` (45 s outage): lost, access point opened as designed, reconnected after 46 s, data resumed.
- *Restarts:* all intentional restarts (Restart Now, display mode change, health restart, after an OTA install) now wait for the SD log to be flushed and unmounted (`sdlog::ejectAndWait`) and set a mark in RTC memory, so the next boot logs "boot after a planned restart". **Quirk found:** on this chip/IDF a plain software restart is often reported by `esp_reset_reason()` as 7 (other watchdog) instead of 3, which made planned restarts look like crashes; the mark settles it. A real crash is still recognised (reason 6/5/4 or 7 without the mark) and logged with each task's last step.
- *First-boot PIN:* the web PIN and setup-Wi-Fi password were only saved with the first settings change, so a radar that was never touched could show a different PIN after each restart. They are now saved when generated.
**Soak test.** `tools/soak.py poll` polls the radar's web API once a minute (uptime, internal heap and low-water mark, PSRAM, fps, aircraft, data age, signal, reset reason, backlight, emergencies) into a CSV; `tools/soak.py report <csv>` judges it. Pass = 24 h with no restart, no data gap over 3 minutes while online, heap low-water mark >= 25 KB, fps >= 20 in 99 % of the samples, PSRAM within 600 KB of its start (no leak), never unreachable for more than 5 minutes. The first run (2026-10-10 01:00, build 0.8, `docs/soak/soak-2026-10-10.csv`) was stopped after 42 minutes to install the flight-detail features (0.9): 0 restarts, heap low-water 42 KB, no data gaps. **A new 24 h run started 2026-10-10 02:17 on the final 0.9 build** (`docs/soak/soak-2026-10-10b.csv`); the result is added below. **Incident 02:31-02:48:** the poller (not the radar) lost its route to the radar for 17 minutes ("No route to host" from that one long-running process while a fresh process and curl reached it); the radar kept running (uptime counter continuous, serial log shows a 5-second status line throughout with no failed fetch and no Wi-Fi event). ### M7 results (2026-10-09)
**Three ways to update, all into the spare slot (`app0`/`app1`, 6.25 MB each), all protected by the web PIN:**
1. **Phone/PC page** (Firmware section): choose `firmware.bin` (from `firmware/.pio/build/viewe7/`), optional SHA-256, *Install file*. Progress bar in the page and on the radar.
2. **From a link** (same section): the radar downloads `http://` or `https://` itself (HTTPS checked against the built-in CA bundle, redirects followed, e.g. a release asset), optional SHA-256. For a link to a file on your own computer: `python3 -m http.server`.
3. **PlatformIO over Wi-Fi** (`espota`): `RADAR_OTA_PIN=<web PIN> pio run -e viewe7-ota -t upload --upload-port radar.local` (env `viewe7-ota` in `platformio.ini`). The radar advertises as `radar`, password = web PIN. A computer connected to the same network twice (Wi-Fi + Ethernet) can make espota stall at 0-1 %: the radar calls back to the address the invitation came from and the reply path may use the other interface. Disconnect one, or use way 1 or 2.
**Never half-installed.** The file is first collected completely in PSRAM (4.9 MB; the largest free block afterwards is ~880 KB), then checked **before flash is touched**: ESP image header and chip (ESP32-S3), segment walk, the image's own appended SHA-256, and your SHA-256 if given. A rejected file costs nothing: the spare slot is not even erased, so "previous firmware" stays valid. If PSRAM cannot hold the file (or its size is unknown) the data is streamed straight into flash instead (same checks at the end, then the spare slot is invalidated if they fail). While an update runs the ADS-B fetch pauses.
**Display during an update (user report, phone video):** every flash erase/write switches the cache off for milliseconds, which starves the display's bounce-buffer interrupt (it copies from the PSRAM frame buffer), so streaming straight to flash tore the picture for the whole minute (repeated lines, doubled text). Now: *receiving* is a normal clean screen with a progress bar (flash is not touched, ~30 s over Wi-Fi), then *"Installing: about 40 seconds"* for 2.5 s, then the flash burst with a **plain rising fill** (nothing with detail, so nothing to tear; the same fill is shown during an espota update), then "Installed. Restarting..." and a restart.
**Safety net (bootloader rollback is enabled in the Arduino core, verified):** a freshly installed image is *pending*. It is confirmed (`esp_ota_mark_app_valid_cancel_rollback`) only after it has run 60 s **with live data** (or 10 minutes with no network); `verifyRollbackLater()` is overridden so Arduino does not confirm at start-up. A reset before confirmation (crash, watchdog, power loss) makes the bootloader return to the previous image by itself. New updates are refused while the running image is still pending ("try again in a minute"). **Previous firmware** button (page): boots the other slot again.
**Tests (all on the real board, web page API with curl, link from this Mac, espota):**
| Test | Result |
|---|---|
| Upload without logging in | 401, nothing written |
| Web upload of a good image (4.9 MB) | installed, restarted into the other slot, `pending`, confirmed after 60 s |
| Wrong SHA-256 (web, link) | rejected, running firmware and "previous" slot untouched |
| Truncated file, corrupted file (one byte flipped), wrong chip id, garbage file | each rejected with a readable message, before flash was touched (garbage is rejected at the first chunk) |
| Link download with correct SHA-256 | installed and confirmed; truncated file from a link rejected |
| **Image that crashes right at start-up** | `abort()` at boot, bootloader returned to the previous image, radar normal again |
| **Image that crashes 25 s after start (before confirmation)** | same: rolled back automatically |
| espota (PlatformIO protocol) | installed over Wi-Fi |
| Previous firmware button / request with no previous | switched slot / 409 "There is no previous firmware" |
Timing: ~30 s receive + ~40 s install = ~75 s for a web upload. Test builds: `-DFW_VERSION="0.7-xxx"` sets the version string, `-DOTA_TEST_MODE=1|2` makes an image crash at start / 25 s after start (the release build contains neither).
**Memory:** internal heap unchanged (idle ~60 KB); the staging buffer is PSRAM only.

### M5b results and flight routes (2026-10-09)
**Map overlay** (Settings > Radar > Map Overlay, also on the phone page; default off): coastlines, land borders and airports (Natural Earth 1:10m, public domain; 489,233 line points in 15,159 chunks + 880 airports, packed by `tools/build_map.py` into a 2.2 MB flash file) drawn into the static layer behind the rings, scale and labels, with the same azimuthal-equidistant projection the aircraft use, so a coast line and an aircraft crossing it agree. Only the chunks whose bounding box touches the radar circle are decoded; segments are clipped to the disc; works across the antimeridian. Airports: diamond + IATA code (mid/major airports, and all of them at ranges up to 80 km). It follows a new location, a new range, a palette change and the unit switch (all rebuild the static layer). **Cost:** a rebuild takes 28-80 ms depending on range and coast density; per-frame cost is zero (measured 30 fps, work 8-16 ms with the overlay on, same as before). **Verified** by rendering the same data on the Mac with the same formulas and comparing pixel by pixel with a framebuffer capture (429 of 471 expected coastline pixels present within 2 px; the rest of the coast-coloured pixels are airport markers and labels). Colour (user request, 2026-10-09): light grey - coastlines and airports RGB 150,150,150, borders 100,100,100 - so the overlay stands apart from the radar colour whatever palette is chosen (`cMap` / `cMapB` in `loadPalette()`, `radar.cpp`).
**Flash:** 4.79 MB of the 6.55 MB app slot (map data 2.2 MB, places/airlines/page/Leaflet ~1 MB). Enough for OTA (M7) as long as the image stays below the slot size; no further large datasets without a size check.
**Flight route on the aircraft card:** select an aircraft with an airline-style callsign (three letters + digit) and the radar asks adsbdb.com (`/v0/callsign/<callsign>`, free community service, answer ~0.5 KB) for origin and destination; the card shows e.g. "SPX Giza  >  MCT Muscat" (IATA code + city) while "Route: looking up..." is shown until the answer arrives. The request runs in the data task between aircraft fetches (one secure connection at a time, so the heap low-water mark is unchanged), results are cached (24 entries; known routes for 1 hour, misses 10 minutes). Callsign-based routes are schedule data: a reused or changed flight number can show a wrong or no route. Privacy: only the callsign of the aircraft you tap is sent. Photos are not included (see `DATA_SOURCES.md`).
**Dev:** `[map]` and `[route]` log lines show draw times and lookups.
